# 怎么读 analysis.json

`analyze.mjs` 的输出。字段不多，但每个字段背后都有一条"为什么这么算"的取舍，
挖新发现之前先读懂这些取舍，否则很容易得出**看起来很硬其实是误报**的结论。

---

## confidence · 置信度

```json
{ "level": "A", "label": "系统可读", "note": "…" }
```

判据是**语义 token 数**（已滤掉 CSS-in-JS 编译原子）。这是全文最重要的字段：

- **A（≥60）** —— 读到的是人家的设计系统本身。可以写"他们定义了"
- **B（15–59）** —— 系统露出一角。判断降调，token 只作旁证
- **C（<15）** —— **只能写"实测出现"**。这时报告是"页面统计"，不是"系统解剖"

C 级不代表做不了，代表**换一种说法**。把这条写进报告开头，别让读者误会你读到了规范。

## 改 probe 之前先读这段：颜色格式

`getComputedStyle` 返回的**不一定是 `rgb()`**。实测 tailwindcss.com：
`lab()` 出现 2335 次、`rgba()` 2151 次、`rgb()` 303 次、`oklab()` 149 次。
只用正则匹配 `rgb()` 的话，**这类站的色板会整个变空**（实测从 40 个色掉到 2 个）。

也**不能靠 canvas 的 `fillStyle` 序列化来转换**。现在的 Chrome 会把
Color Level 4 的值原样吐回来：

```js
ctx.fillStyle = 'lab(87.8405% 13.4282 -18.7159)';
ctx.fillStyle  // → 'lab(87.8405 13.4282 -18.7159)'，不是 hex
```

**可行的只有真画一个像素再读回来**：

```js
ctx.clearRect(0, 0, 1, 1);
ctx.fillRect(0, 0, 1, 1);
const [r, g, b, a] = ctx.getImageData(0, 0, 1, 1).data;
```

浏览器认得的格式它全认，不用跟着 CSS Color 规范追。代价是超出 sRGB 的
广色域色（`color(display-p3 …)`）会被夹回 sRGB —— 对出色板来说可以接受。

非法值要先用两个哨兵验一遍：赋非法值时 `fillStyle` 保持不变，
用两个不同初值各跑一遍，结果不一致就说明浏览器不认这个值。

同一套归一化也用在 token 值上（输出为 `varColors`）。不这么做的话，
用 `lab()`/`oklch()` 写 token 的站没法把实测色追回 token，
色板会**全部**被标成「野色」—— 那是误报，不是发现。

## neutrals · 中性色

一套系统对中性色的处理最能说明成熟度：随手 `#888`，还是每一档都调过色相。

| 字段 | 含义 |
|---|---|
| `tintedCount` | 带彩度的中性色个数 |
| `pureGreys` | 彩度为 0 的中性色。**已排除纯白纯黑** |
| `clusters` | 按 30° 分档的色相族，带成员数和平均彩度 |
| `brand` | 品牌色。优先取 `--color-brand*` / `--accent*` 这类 token 声明的值 |
| `intentional` | 中性色是否**有意从品牌色派生** |

**两个坑，改判据前先想清楚**：

1. **纯白纯黑必须排除在 `pureGreys` 之外**。它们无彩度是数学必然，不是设计选择。
   不排除的话"中性色里混了纯灰"这条发现在每个站都会误报。
2. **品牌色不能靠彩度排序取**。彩度最高的常常是个报错红或高亮荧光色，
   只用了十几次。先信 token 命名，退回时也是按**用量**排，不是按彩度。

`intentional = true` 需要同时满足：有带彩中性色、纯灰不超过 1 个、
主色相族有 60% 以上落在品牌色 ±90° 内。三条缺一条就不成立 —— 宁可不报也别硬报。

## typography · 排版

| 字段 | 含义 |
|---|---|
| `weights` / `offHundred` | 实测字重，以及其中不是整百的。后者是可变字体的痕迹 |
| `curve` | 字号阶梯，每档带 `px` / `trackEm` / `lhRatio` |
| `curveSource` | `token`（读的声明值）还是 `measured`（读的实测值） |
| `familyCurves` | 按 token 族拆开的平行阶梯 |
| `steps` | 字距的台阶 |
| `lhTrend` | 小字与大字的平均行高，用来判断行高是否随字号收紧 |

### 各家的 token 命名约定都不一样

`declaredTypeScale()` 要同时认下面四种写法。只认其中一种的话，另外几家的站会白白退回实测曲线：

| 写法 | 长什么样 | 谁在用 |
|---|---|---|
| **后缀式 · kebab** | `--title-3-size` / `--title-3-line-height` | Linear |
| **后缀式 · 驼峰** | `--hds-font-heading-md-lineHeight` | Stripe |
| **双短横线修饰符** | `--text-sm: .875rem` + `--text-sm--line-height` | Tailwind v4 |
| **font 简写** | `--title-7: 590 3.5rem / 1.1 "Inter…"` | Linear |

后缀一律归一化后再比对（小写、去掉短横线），别为每家写一条正则。

两个必须处理的细节：

1. **`size` 后缀太通用，必须加排版类关键词才收**。
   `--scrollbar-size: 6px`、`--min-tap-size: 44px` 都会命中，收进来就成了假字号。
2. **行高常常是 `calc()` 比值**。Tailwind 写 `calc(1.25 / .875)` —— 不求值就读不出来。
   只需支持 `calc(a / b)` 和 `calc(a * b)` 两种，够用了。

**族名取「去掉最后一段」，不是第一段。** 最后一段是阶梯档位（`md` / `3` / `sm`），
前面才是族。取第一段的话，Stripe 的 703 个 token 会全挤进一个 `hds` 族；
去掉尾段才能正确拆成 `hds-font-text` / `hds-font-heading` / `hds-font-input-text`。

**只有字号、没有行高也没有字距的族要丢掉。** Linear 同时有裸的 `--font-size-*` 阶梯
和复合的 `--title-*` / `--text-*` 阶梯，前者是低信息重复品，留着会挤掉真正的阶梯。

---

**关键取舍：阶梯优先从 token 读，不是从实测读。**

实测拿到的是浏览器算完的结果，噪音大到看不出台阶。同一份 Linear 数据：

- 实测曲线 → 检出 **7 个台阶**（全是噪音，等于没有台阶）
- token 曲线 → 检出 **1 个台阶**（24px→32px，字距翻倍，真实存在）

**另一个关键取舍：必须按族分开算。**
一个系统可以有好几套平行阶梯（`--text-*` 正文档、`--title-*` 标题档）。
混进一条曲线按字号排序，族与族交叉的地方会**伪造出根本不存在的台阶**。

一族里超过 2 个台阶，说明这族压根没有台阶，全部丢弃 —— 别硬讲故事。

## findings · 发现

三类，报告里按这个顺序排：

| kind | 是什么 | 为什么值钱 |
|---|---|---|
| `drift` | token 写的和页面跑的对不上 | **只有全量测量能撞见**，人眼读 CSS 读不出来 |
| `signature` | 这个站跟别人不一样的地方 | 有辨识度，是"性格" |
| `craft` | 做得讲究的细节 | 可学习，但不稀缺 |

每条含 `id` / `title` / `body` / `data`。`body` 是写好的中文句子，可以直接用；
`data` 是原始数据，要自己重新组织表达时用它。

### 五种漂移检测

| id | 在查什么 | 阈值 / 注意 |
|---|---|---|
| `duration-rogue` | 实测动画时长不在 token 表里 | 只看 <1s 的。更长的多是环境动效，不算漂移。**比较前要归一化**：`.15s` / `0.15s` / `150ms` 是同一个值 |
| `ease-deadstock` | 定义了但没人用的缓动 | 至少定义 3 条才查。**比较前归一化 cubic-bezier 的四个数** —— `.25` 和 `0.25` 是同一条曲线 |
| `color-rogue` | 追不到任何 token 的高频色 | 只算 `count ≥ 5` 的。渐变插值出来的一次性色追不到是正常的 |
| `neutral-outlier` | 一堆调过色相的中性色里混进的纯灰 | 纯灰 1–2 个才报。满地都是就不叫"漏网"了 |
| `space-offgrid` | 不在基数网格上的高频间距 | 基数 **必须 ≥4**。2px「网格」在数学上永远成立，说了等于没说 |

写代码加新检测时，**先问一句"这条在一个做得很好的站上会不会误报"**。
会误报的检测比没有检测更糟 —— 它会让整份报告失去可信度。

## spacing · 间距网格

```json
{ "base": 4, "coverage": 0.73, "measured": [[8,132],[32,130],…] }
```

`base` 是猜出来的基数，`coverage` 是落在网格上的**频次占比**（不是种类占比）。

两处讲究：

1. **按出现次数加权**。用了 132 次的 8px 和只出现 1 次的 19px 不该同权
2. **只认 ≥4 的基数**。返回 `base: 0` 表示这个站没有可辨认的网格 ——
   这本身就是一条结论：间距是一处一处写出来的，不是从系统里取的

## 自己挖新发现

`an.json` 里没被用上的数据还有不少，值得挖的方向：

- **`states`** —— hover / focus / active 各自改了哪些属性。
  "这个站 hover 只改 background 和 opacity，全程不碰 transform" 是很能说明性格的一句话
- **`shadows`** —— 多层叠加阴影（一条 box-shadow 里 4–5 层）是在模拟真实光照，
  单层 `0 2px 4px` 是随手写的。这个对比很直观
- **`radii`** —— 圆角是不是一个等比或等差数列。混着 `50%` 和 `9999px` 说明两拨人写的
- **`filters`** —— 有 `backdrop-filter` 说明用了毛玻璃，值多大决定了质感
- **`otherPasses`** —— 多视口/多主题采集时的对比数据。移动端色板和桌面不一样是个信号

挖的时候守一条：**结论必须能追回到具体数值**。
说"这个站很克制"没用，说"只用了 4 档动画时长，最长 0.25s"才有用。
